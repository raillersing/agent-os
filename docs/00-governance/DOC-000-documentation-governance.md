# DOC-000 — Agent OS Documentation Governance and Source-of-Truth Policy

## 1. Purpose

This document defines how Agent OS documentation is identified, written, reviewed, approved, versioned, implemented, superseded, archived, and validated.

Its purpose is to prevent contradictions, undocumented architectural drift, unverifiable implementation claims, and loss of project decisions across conversations, agents, repositories, and releases.

## 2. Scope

This policy applies to:

- product and business documents;
- functional and non-functional requirements;
- architecture descriptions and diagrams;
- Architecture Decision Records;
- API, event, schema, plugin, agent, model, artifact, memory, and approval contracts;
- security and AI-governance policies;
- UX specifications and design-system documents;
- development, testing, release, and operational documents;
- user documentation;
- acceptance and assurance evidence.

It applies to documents written by humans, AI agents, scripts, or generated from source code.

## 3. Governing principles

### 3.1 One authoritative source per subject

Every controlled subject must have an identified source of truth. Supporting documents may summarize it but must link back to the authoritative document.

### 3.2 Approval is explicit

A document is not approved because it exists, appears complete, was generated by an agent, or was committed to Git. Approval must be explicitly recorded through the project’s approved review process.

### 3.3 Claims require evidence

Documentation must not state that functionality, tests, integrations, migrations, security controls, or production readiness exist unless evidence is available.

### 3.4 Requirements are testable

Mandatory requirements must use stable identifiers and include measurable acceptance conditions.

### 3.5 Decisions are preserved

Architecturally significant decisions must be recorded as ADRs. Approved decisions must not be silently rewritten when the architecture changes.

### 3.6 Contracts are executable where practical

Interfaces should be represented in machine-readable form when a suitable standard exists, including OpenAPI, AsyncAPI, JSON Schema, policy-as-code, and versioned event schemas.

### 3.7 Documentation evolves with implementation

Documentation is part of the product. A feature is not complete when required documentation, contracts, tests, migration notes, operational procedures, or evidence are missing.

### 3.8 Vendor neutrality

Documents must describe capabilities and contracts before selecting implementations. Vendor-specific behavior belongs in adapter or deployment specifications unless it is an approved platform decision.

## 6. Document statuses

| Status | Meaning |
|---|---|
| `draft` | Work in progress; not authoritative |
| `in-review` | Submitted for formal review |
| `approved` | Explicitly approved and authoritative for its scope |
| `implemented` | Approved and verified as reflected in the implementation |
| `deprecated` | Still readable but should not guide new work |
| `superseded` | Replaced by a named document or decision |
| `archived` | Retained for history only |

Status transitions must be explicit and reviewable.

## 7. Versioning

Controlled documents use semantic-style versions:

- major: meaning, scope, contract, or approved direction changes incompatibly;
- minor: new requirements, sections, or compatible clarifications;
- patch: corrections that do not change meaning.

Examples:

```text
0.1.0  Initial draft
0.2.0  Substantial review update
1.0.0  First approved baseline
1.1.0  Approved compatible extension
2.0.0  Superseding architecture or requirement baseline
```

Git commit hashes and release tags provide repository history but do not replace the document version.

## 8. Source-of-truth hierarchy

When sources conflict, use the following precedence unless an approved ADR states otherwise:

1. approved machine-readable contracts and policies;
2. approved ADRs;
3. approved requirements and architecture baselines;
4. approved module and adapter specifications;
5. verified implementation and automated tests;
6. user and operational documentation;
7. drafts, conversations, prompts, agent memory, and informal notes.

A conflict between an approved contract and implementation is a defect that must be resolved; it is not permission to choose whichever source is convenient.

## 9. Roles

### Product owner

- approves product vision, scope, priorities, user journeys, and business rules;
- accepts or rejects product-level risks;
- gives final acceptance for user-visible behavior.

### Architecture owner

- maintains architecture coherence;
- reviews system boundaries and significant decisions;
- requires ADRs where appropriate.

### Security owner

- reviews threat models, permissions, sandboxing, secrets, data classification, and production controls;
- accepts or escalates security risks.

### Document owner

- maintains accuracy, links, review state, and change history for a document.

### Implementer or agent

- may draft and propose changes;
- must not self-approve controlled documents;
- must provide implementation and validation evidence.

### Reviewer

- checks correctness, consistency, completeness, traceability, and evidence;
- must identify unresolved assumptions and contradictions.

## 10. Required document workflow

```text
Proposed
  → Drafted
  → Self-checked
  → Cross-document consistency checked
  → Submitted for review
  → Review comments resolved
  → Explicitly approved
  → Implemented
  → Verified against evidence
  → Maintained or superseded
```

A document may return to draft after material review findings.

## 11. Architecture Decision Records

Create an ADR when a decision:

- changes a system boundary;
- adopts or removes a protocol, runtime, database, gateway, security mechanism, or deployment strategy;
- creates a long-term constraint;
- affects several modules or teams;
- has important trade-offs or migration consequences;
- supersedes an earlier architecture decision.

ADRs are immutable historical records after acceptance. A changed decision requires a new ADR that supersedes the old one.

## 12. Requirements control

Every mandatory requirement must include:

- stable identifier;
- title;
- rationale;
- priority;
- actors;
- preconditions;
- expected behavior;
- failure behavior;
- security or approval implications;
- measurable acceptance criteria;
- related architecture and tests.

Requirements must avoid ambiguous terms such as “fast,” “easy,” “secure,” “modern,” or “user-friendly” without measurable interpretation.

## 13. Traceability

The minimum traceability chain is:

```text
Product objective
→ Requirement
→ Architecture component
→ Contract or schema
→ Backlog item
→ Code change
→ Automated or manual test
→ Acceptance evidence
→ Release
```

The traceability matrix must not claim links that have not been verified.

## 14. Citations and external references

- Prefer standards bodies, official specifications, official product documentation, and primary research.
- Record the accessed version or date when external behavior may change.
- Do not invent citations or cite a source that does not support the claim.
- Distinguish mandatory project decisions from informative external guidance.
- Maintain adopted standards in a standards register.

## 15. AI-generated documentation controls

AI-generated content is always a draft until reviewed.

Agents must:

- identify assumptions and unresolved questions;
- avoid fabricated implementation status, metrics, tests, diagrams, and citations;
- inspect repository evidence before documenting existing behavior;
- preserve approved terminology and identifiers;
- avoid replacing approved content without an explicit change request;
- report validation failures truthfully.

Agents must not:

- approve their own documents;
- infer production readiness from a prototype or screenshot;
- mark requirements implemented solely because UI elements exist;
- expose secrets or personal data in documentation;
- rewrite history to hide superseded decisions.

## 16. Documentation Definition of Done

A controlled document is complete for its declared version only when:

- required metadata is valid;
- the identifier is unique and registered;
- scope and audience are clear;
- terminology matches the glossary;
- mandatory statements are testable where applicable;
- assumptions and open questions are explicit;
- links and references resolve;
- related requirements, ADRs, contracts, tests, and evidence are linked where relevant;
- contradictions with approved documents are resolved or recorded;
- required reviewers have approved it;
- automated documentation checks pass.

## 17. Change policy

Minor editorial corrections may be made through a documentation-only change.

Material changes require:

1. change rationale;
2. impacted-document analysis;
3. updated version;
4. updated traceability;
5. review by affected owners;
6. migration or compatibility notes when applicable.

## 18. Repository validation

At minimum, automated checks should verify:

- valid YAML front matter;
- unique document identifiers;
- registered documents exist;
- no duplicate IDs;
- required metadata fields;
- valid status values;
- internal link integrity;
- schema validity where applicable;
- unresolved placeholders in approved documents;
- traceability references where required.

## 19. Initial approval criteria for version 1.0

This document may move to `approved` version `1.0.0` after:

- the project owner confirms the source-of-truth hierarchy;
- document prefixes and statuses are accepted;
- approval roles are confirmed;
- versioning and ADR rules are accepted;
- the document register and validation script align with this policy;
- no unresolved governance issue blocks the first documentation wave.
